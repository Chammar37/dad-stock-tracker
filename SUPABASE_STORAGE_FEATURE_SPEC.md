# Feature Spec: Supabase Storage Backend

Last updated: 2026-08-08

## Goal

Update the Streamlit stock tracker so trade and holdings data can be stored securely in the Supabase project instead of local CSV files.

The target user is non-technical. The deployed app should require no local setup for the user beyond opening the Streamlit app URL and signing in or entering an app password.

## Recommendation

Use Supabase Postgres as the app's persistent storage backend.

For the first implementation, keep the existing `DataManager` public methods and replace or wrap the CSV implementation with a Supabase-backed implementation. This minimizes changes to `app.py` and `TradeCalculator`.

## Credential Storage

Credentials must never be committed to Git.

Local development credentials should live in:

```text
.streamlit/secrets.toml
```

Streamlit Cloud credentials should live in:

```text
Streamlit app dashboard -> Settings -> Secrets
```

Add this to `.gitignore` before creating local credentials:

```gitignore
.streamlit/secrets.toml
```

## Do We Need The Database Password?

It depends on the connection approach.

### Recommended Approach: Direct Postgres Connection

Use Streamlit's built-in SQL connection with SQLAlchemy and Supabase's Postgres connection string.

This approach does require the Supabase database password, usually as part of a single database URL.

Example local `.streamlit/secrets.toml`:

```toml
[connections.supabase]
url = "postgresql+psycopg2://postgres.PROJECT_REF:DB_PASSWORD@aws-0-REGION.pooler.supabase.com:6543/postgres"
```

Pros:

- Uses Streamlit's built-in `st.connection(..., type="sql")`.
- Uses normal SQL transactions.
- Fits the existing relational data model.
- Easier to keep holdings and trades consistent.

Cons:

- Requires storing the database password securely in Streamlit secrets.

### Alternative Approach: Supabase API Client

Use `supabase-py` with:

```toml
[supabase]
url = "https://PROJECT_REF.supabase.co"
service_role_key = "..."
```

This approach does not require the database password, but it does require a Supabase API key. For server-side writes from Streamlit, the `service_role_key` is powerful and must be treated like a password.

For this app, direct Postgres is simpler and more transaction-friendly.

## Security Requirements

- Store credentials only in Streamlit secrets.
- Do not commit `.streamlit/secrets.toml`.
- Do not print secrets in Streamlit UI or logs.
- Restrict the Streamlit app so only the intended user can access it.
- Use one of:
  - Streamlit Community Cloud viewer access controls, if available for the deployment.
  - A simple app-level password stored in `st.secrets`.
  - Streamlit `st.login()` with an identity provider later, if desired.
- Keep Supabase tables private by default.
- If using direct Postgres from the server, do not expose the database URL to browser-side code.

## Proposed Secrets Shape

Recommended:

```toml
[connections.supabase]
url = "postgresql+psycopg2://..."

[auth]
app_password = "choose-a-strong-password"
```

Optional environment selector:

```toml
[storage]
backend = "supabase"
```

For local-only fallback:

```toml
[storage]
backend = "csv"
```

## Database Schema

Create two tables to match the current CSV files.

### `holdings`

```sql
create table if not exists holdings (
  id bigint generated by default as identity primary key,
  account text not null,
  stock_name text not null,
  stock_symbol text not null,
  quantity integer not null default 0,
  average_price_per_share numeric(18, 6) not null default 0,
  capital_gain_loss numeric(18, 2) not null default 0,
  date_of_acquisition date,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (account, stock_symbol)
);
```

### `trades`

```sql
create table if not exists trades (
  id bigint generated by default as identity primary key,
  account text not null,
  stock_name text not null,
  stock_symbol text not null,
  date_of_trade date not null,
  trade_type text not null check (trade_type in ('B', 'S', 'T')),
  shares_traded integer not null check (shares_traded > 0),
  price_per_share numeric(18, 6) not null,
  commission numeric(18, 2) not null default 0,
  created_at timestamptz not null default now()
);
```

## Suggested Data Access Design

Keep the current `DataManager` interface stable where possible:

- `read_consolidated()`
- `read_trades()`
- `write_consolidated()`
- `write_trades()`
- `add_trade()`
- `delete_trade()`
- `get_trade_at_index()`
- `delete_consolidated_record()`
- `get_trades_for_account_symbol()`
- `update_consolidated_record()`
- `get_consolidated_record()`
- `get_accounts()`
- `get_stock_symbols()`

Add either:

```text
utils/supabase_data_manager.py
```

or refactor `DataManager` to choose a backend:

```python
if st.secrets.get("storage", {}).get("backend") == "supabase":
    data_manager = SupabaseDataManager()
else:
    data_manager = DataManager()
```

Preferred implementation:

- `CsvDataManager`: current CSV behavior.
- `SupabaseDataManager`: same methods, backed by SQL.
- `create_data_manager()`: chooses backend from secrets/env.

## Transaction Requirement

Trade writes should become atomic.

Currently, `TradeCalculator.process_trade()` writes to trade history before confirming the holdings update succeeds. While moving to Supabase, fix this by making trade insert and holdings update happen in a single transaction.

Required behavior:

- Invalid sell does not insert into `trades`.
- Failed holdings update rolls back trade insert.
- Delete trade and rebuild should run transactionally for the affected account+symbol.

## Migration Plan

1. Add `.streamlit/secrets.toml` to `.gitignore`.
2. Add Supabase/Postgres dependencies:
   - `SQLAlchemy`
   - `psycopg2-binary` or `psycopg`
3. Create the `holdings` and `trades` tables in Supabase.
4. Add `SupabaseDataManager` with the same public interface as the current `DataManager`.
5. Add a backend selector.
6. Migrate existing CSV data into Supabase with a one-time script.
7. Run existing tests against CSV.
8. Add equivalent tests for Supabase data-manager behavior, ideally using a test database or mocked SQL layer.
9. Deploy to Streamlit Cloud.
10. Add Supabase connection string and app password to Streamlit Cloud Secrets.

## One-Time CSV Migration

Create:

```text
scripts/migrate_csv_to_supabase.py
```

Behavior:

- Read `data/consolidated.csv`.
- Insert/upsert rows into `holdings`.
- Read `data/trades.csv`.
- Insert rows into `trades`.
- Validate row counts.
- Print a summary without printing credentials.

## User Experience Requirements

- Dad opens a Streamlit URL.
- App prompts for a password or uses Streamlit access control.
- After login, app behaves the same as today.
- Trade entry, trade history, and stock charts should not expose storage backend details.
- Add a backup/export page or button to download holdings/trades as CSV.

## Acceptance Criteria

- App can read holdings from Supabase.
- App can write buy trades to Supabase.
- App can write sell trades to Supabase.
- Invalid sell trades do not create trade rows.
- Consolidated holdings update correctly after buy/sell.
- Trade deletion rebuilds holdings correctly.
- Existing tests still pass.
- No credentials are committed to Git.
- Streamlit Cloud deployment works using Secrets.

## Open Decisions

- Whether to use Streamlit Cloud viewer access controls, app-level password, or both.
- Whether to keep CSV as a fallback backend.
- Whether pre-populated holdings should also create an initial trade row.
- Whether zero-quantity holdings should stay in `holdings` or be hidden/deleted after full sell.
